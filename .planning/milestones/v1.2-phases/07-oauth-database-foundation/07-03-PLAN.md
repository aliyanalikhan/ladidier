<objective>
Put the sign-in requirement in front of the two paid plans — enforced on the server, made to feel
like a flow in the browser — and then verify the whole phase end-to-end on a real deployment.

Purpose: AUTH-04 is the requirement that gives Phase 7 its commercial point. A gate that exists only
in the browser is not a gate, so the authoritative check is a 401 in `api/checkout.js` before any
Stripe call; the client half exists so a signed-out visitor experiences a sign-in and a resume
rather than an error. The closing checkpoint is where all six of the phase's requirements are
confirmed against production rather than against localhost.

Output: a session gate on `POST /api/checkout`, a sign-in-then-resume flow in `SubscribePage`, and a
signed-off end-to-end verification of Phase 7.

Locked decisions this plan implements:
- D-01: the client gate, the pending-plan trampoline and the server 401 are Task 5 of the 260831-8ug draft plan, reused rather than re-derived.
- D-02: the draft's Task 6 address work is out of scope — no 409 branch, no address form, no second table, and Stripe's own shipping and phone collection for Hard Copy is left in place.
- D-03: the draft's Stripe-customer-linkage additions to `sessions.create` are deferred to Phase 8; this phase's change to `api/checkout.js` is the session gate and nothing else, because the draft's approach is the exact duplicate-customer anti-pattern research flagged.
- D-07: the sign-in failure path is verified in the closing checkpoint as producing no visible error copy at all.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> POST /api/checkout | The only thing standing between a visitor and a paid Stripe Checkout Session. Callable directly with curl, with any headers the caller chooses. |
| sessionStorage -> checkout invocation | A pending-plan intent written before a redirect and read back after it; the visitor controls its contents. |

## STRIDE Threat Register

ASVS level: 1 · Block-on severity: high

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-03 | Elevation of Privilege | `api/checkout.js` | critical | mitigate | The gate is enforced server-side as a 401 from `readSession` before any Stripe call; the branch in `handleSelectPlan` is convenience only and carries no authority. Verified by a cookie-less curl in Task 1's human check and again in Task 3 path 6. |
| T-07-19 | Tampering | `ladidier_pending_plan` in sessionStorage | low | mitigate | The stored value only chooses which plan key the client re-submits; the server re-validates that key against `PRICE_ENV` and re-checks the session on the resumed request, so a tampered intent can at worst pick a different legitimate plan the visitor could have clicked anyway. The parse is wrapped in try/catch and a malformed value is discarded. |
| T-07-20 | Denial of Service | pending-plan resume loop | low | mitigate | The key is removed from sessionStorage before it is acted on, so a checkout that fails cannot re-trigger itself on the next load, and an abandoned intent dies with the tab. |
| T-07-21 | Information Disclosure | 401 response body | low | accept | `{ error: 'Sign in to subscribe' }` states only that authentication is required — it reveals no plan pricing, no configuration, and no distinction between "no cookie", "bad cookie" and "expired cookie". Accepted as the minimum useful message. |
| T-07-11 | Repudiation | Stripe subscription <-> user linkage | low | accept | Phase 7 deliberately creates no audit link between a Checkout Session and a `users` row (D-03) — `customer_email` is the duplicate-customer anti-pattern this milestone's research flagged. Accepted because entitlement remains Stripe's answer exactly as it is today and no new claim depends on that trail; Phase 8 delivers the link properly via a stored customer id. |
| T-07-SC | Tampering | package-manager installs | n/a | mitigate | No `npm install` occurs in this plan — it adds no dependency. The phase's single new package was gated by the blocking human legitimacy checkpoint in 07-01-PLAN.md Task 1. |
</threat_model>
