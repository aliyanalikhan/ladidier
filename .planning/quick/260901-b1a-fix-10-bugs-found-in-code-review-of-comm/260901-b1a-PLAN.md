<objective>
Fix the 10 defects found in the code review of commit a850d59 (Phase 7-9 OAuth / database / Stripe-linking / account-page work), in three priority-ordered tasks: four correctness-critical access and session bugs, two data-integrity bugs, and four cleanup bugs.

Four fixes, in this order.

(a) BUG-03 — cookie decode guard. In `lib/membership.js`, `readCookie` currently calls `decodeURIComponent` unguarded, so a malformed percent sequence throws a URIError up through every caller. Wrap the decode of the matched value so that a decode failure yields `null` (the same answer as "cookie absent"), not a throw. Do not change the behaviour for well-formed values: a valid value still decodes exactly as before, and an empty decoded string still collapses to `null`. Then in `lib/session.js`, make the documented never-throws contract actually true by moving the opening of `readSession`'s existing `try` to the very top of the function body so the `readCookie` call and the two early `return null` guards sit inside it; keep the existing `catch` returning `null`. Both layers are needed: the guard fixes every other `readCookie` caller (api/entitlement.js and api/auth/callback.js read cookies the same way), and the restructure keeps `readSession` honest for any future call it grows.

(b) BUG-01 — one gate that honours both paths. Create `lib/access.js` exporting `async function hasIssueAccess(request, stripe)`. It resolves in this order: first await the legacy check `checkActiveMembership(request, stripe)` and return `true` immediately if it grants — this costs zero Stripe calls when no member cookie is present, so it is strictly cheaper than the reverse order and leaves legacy behaviour byte-identical. Only if legacy declines, read the session from `request.headers.get('cookie')` via `readSession`; with no session, return `false`; with a session, return the result of `checkUserActiveMembership({ userId: session.uid, stripe })`. Wrap that entire account branch in a `try` that returns `false` on any throw — `getUserById` runs outside `checkUserActiveMembership`'s own try and will throw if the database env var is missing, and an issue route must fail closed with 403, never 500. Then change `api/issue/pdf.js` and `api/issue/page.js` to call `hasIssueAccess(request, stripe)` in place of their current legacy-only call, importing it from the new module and dropping their now-unused legacy import. Nothing else in either route changes: the same 403 body, the same `PRIVATE` headers, the same page-number bounds validation, the same file reads.

(c) BUG-02 — one membership resolver in `src/app.jsx`. Two `useEffect` hooks currently write `isMember` from two independent async sources, so whichever settles last wins and a real member can be locked out. Delete both effects (the legacy `/api/entitlement` effect and the `user`-gated `/api/account/status` effect) and replace them with a single effect keyed on `[authReady, user]` that owns `isMember` outright. Keep the existing 6-hour recheck skip verbatim: read `ladidier_member_checked`, and if `isMember` is already true and the stored timestamp is newer than the 6-hour window, return without asking. Otherwise bail out until `authReady` is true, then issue both requests together under one `Promise.all`, mapping each response to a tri-state: `true`, `false`, or `null` for a network/parse failure. The account request is only sent when `user` is set; with no signed-in user its result is a definitive `false`, not `null`. Resolve with this table, evaluated once: if either source is `true`, set `isMember` true, write `ladidier_member`, and stamp `ladidier_member_checked`; else if both sources are definitive (neither is `null`), set `isMember` false, remove `ladidier_member`, and stamp `ladidier_member_checked`; else (at least one source unknown) leave state and storage untouched, preserving the existing "a dropped connection must not lock out a paying member" behaviour. Keep the `cancelled` flag guard on the resolution. Read `isMember` directly for the recheck skip and deliberately leave it out of the dependency array — adding it would re-fire the effect on its own write. The Stripe-return `verify-session` effect keeps its own `setIsMember(true)`; it is a distinct one-shot post-checkout writer, not a competing poller.

(d) BUG-04 — sign-out must not leave paid access behind. In `src/pages.jsx`, add one module-scope helper `clearMemberLocalState()` next to the existing `PENDING_PLAN` constant that removes `ladidier_member`, `ladidier_member_checked`, and `ladidier_subscribed` from localStorage. Call it from both sign-out handlers, in the `finally`/post-logout position after the logout request settles. `AccountPage.handleSignOut` then keeps its existing full navigation to `/`. `SubscribePage.handleSignOut` currently only calls `setUser(null)`, which leaves App's in-memory `isMember` true even after storage is cleared — so after clearing, have it navigate to `/#subscribe` via a full page load instead, which remounts App against the cleared storage and keeps the visitor on the page they were on. Do NOT clear the httpOnly Stripe member cookie from the server on logout: that cookie is the legacy device-bound entitlement earned by a purchase made in this browser, it is what the ROADMAP regression invariant protects, and the shared-computer case in this finding is the account-path member, who has no such cookie.
