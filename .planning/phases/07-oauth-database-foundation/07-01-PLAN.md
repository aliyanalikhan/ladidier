<objective>
Stand up the identity layer this project has never had: a real Postgres `users` table keyed on
the Google account id, an HMAC-signed httpOnly session cookie, and a hand-rolled Google OAuth
flow over four small serverless routes — proven end-to-end on a single sign-in path before any
UI is built on top of it.

Purpose: today the site knows a visitor only by an opaque per-browser Stripe cookie. AUTH-01,
AUTH-02, AUTH-03, ACCT-01 and ACCT-02 all need a persistent person behind the browser. This plan
is the tracer slice for the whole phase — it touches every layer Phase 7 will modify (npm
dependency, Postgres, session crypto, serverless routes) on exactly one path, so an architectural
dead-end surfaces after one commit rather than after the client work is already committed on top.

Output: `@neondatabase/serverless` installed, a one-table schema plus `lib/db.js`, `lib/session.js`,
`scripts/db-setup.mjs`, and `api/auth/google.js` / `callback.js` / `me.js` / `logout.js`.

Locked decisions this plan implements:
- D-01: Tasks 1-3 here are Tasks 1-3 of the 260831-8ug draft plan, reused as the technical foundation rather than re-derived — package legitimacy gate, Vercel Postgres + Google OAuth provisioning, and the schema/session/four-routes tracer.
- D-02: the draft's second table, `lib/shipping.js` and `api/address.js` are out of scope; `SCHEMA_SQL` holds exactly one DDL statement and the verify gate asserts the public schema has exactly one table.

**lib/db.js** — the only module that knows the schema.
Export a lazy `sql` wrapper, not a module-scope `neon(...)` call. Follow the reference plan's code
block verbatim: a module-level `_sql` memo, a `getSql()` that reads `process.env.DATABASE_URL ||
process.env.POSTGRES_URL` and throws a named `Error` when neither is set, and
`export const sql = (...args) => getSql()(...args)` plus `sql.query = (...args) => getSql().query(...args)`
so call sites can keep writing tagged templates while the env-var read stays deferred to first use.

Export `SCHEMA_SQL` as an array of exactly one `create table if not exists users` DDL string with
these columns in this order: `id bigint generated always as identity primary key`,
`google_sub text not null unique`, `email text not null`, `name text`, `picture text`,
`created_at timestamptz not null default now()`, `last_login_at timestamptz not null default now()`.
The `unique` on `google_sub` is what makes ACCT-02 structurally true rather than merely intended —
it is the conflict target the upsert needs and the constraint a race between two tabs hits.

Export `ensureSchema()`, memoised in a module-level promise so the DDL costs one round trip per
warm instance and nothing after. Run each statement with `sql.query(stmt)` — the tagged template is
for parameterised values, `.query()` for these fixed DDL strings. On failure, reset the memo to
null before rethrowing, otherwise one cold-start blip poisons the instance for its whole life.
Record that reasoning in a comment.

Export `upsertUser({ sub, email, name, picture })`: a single
`insert into users (google_sub, email, name, picture) values (...) on conflict (google_sub)
do update set email = excluded.email, name = excluded.name, picture = excluded.picture,
last_login_at = now() returning id, email, name`. The Neon tagged template returns the row array
directly — it is NOT the `{ rows }` shape of the deprecated `@vercel/postgres` — so read
`rows[0]`. Comment why this is an upsert rather than select-then-insert: sign-in is the only write
path and a race between two tabs must not create two accounts (ACCT-02).

Add `"db:setup": "node --env-file=.env.local scripts/db-setup.mjs"` to package.json `scripts`.

**scripts/db-setup.mjs** — imports `ensureSchema` from `../lib/db.js`, awaits it, logs the table it
applied, exits 0. Node 22's built-in `--env-file` loads the connection string from `.env.local`, so
no dotenv dependency is needed.

**lib/session.js** — the session cookie and the OAuth state cookie.
Export `SESSION_COOKIE = 'ladidier_session'` and `OAUTH_STATE_COOKIE = 'ladidier_oauth_state'`.
Neither may collide with `ladidier_member_session` from lib/membership.js; the two systems are
independent and a member who signs out of Google keeps their paid access. Import `readCookie` from
`./membership.js` rather than writing a second cookie parser.

Export a single module constant `SESSION_TTL_SECONDS = 7 * 24 * 60 * 60` and derive BOTH the
payload `exp` and the Set-Cookie `Max-Age` from it. One constant, two consumers — a drift between
them produces a cookie the browser keeps sending and the server always rejects, which reads as a
random logout. Comment that this is a flat 7-day expiry from sign-in with no renew-on-activity
(D-06).

Session value format: `base64url(JSON.stringify(payload)) + '.' + base64url(hmac)`, payload
`{ uid, email, name, exp }`. Build the HMAC key lazily with
`crypto.subtle.importKey('raw', ..., { name: 'HMAC', hash: 'SHA-256' }, false, ['sign'])` from
`process.env.SESSION_SECRET`, throwing a named error when the secret is absent — same lazy pattern
and same reasoning as `getStripe()`.

Export `signSession(payload)` and `readSession(cookieHeader)`, both async. `readSession` returns the
payload or null: it recomputes the HMAC and compares with a constant-time loop (accumulate a XOR
difference across all bytes, test once at the end — a short-circuiting `===` on the signature leaks
how much of a forgery was correct), and rejects an `exp` in the past. Any malformed input returns
null rather than throwing; a garbage cookie is an anonymous visitor, not a server error.

Export `sessionCookie(value)` and `clearSessionCookie()` producing Set-Cookie strings with
`Path=/; HttpOnly; Secure; SameSite=Lax` and `Max-Age=${SESSION_TTL_SECONDS}` (clear uses
`Max-Age=0`). Export `stateCookie(value)` and `clearStateCookie()` the same way but with
`Path=/api/auth` and `Max-Age=600`. SameSite must be Lax on both, never Strict: the browser arrives
back from accounts.google.com as a cross-site top-level GET, and Strict would withhold the state
cookie and break every sign-in. Say that in a comment so nobody "hardens" it later.

**api/auth/google.js** (`export async function GET(request)`) — start the flow.
Read `GOOGLE_CLIENT_ID` and `SESSION_SECRET`; if either is missing, `console.error` the specific
name and return a 500 with an opaque message, matching api/checkout.js's ordering. Read the
`returnTo` query parameter and accept it only when it matches `/^[a-z]+$/` (these are hash route
names such as `subscribe`), defaulting to `subscribe` — this regex is what stops the parameter
being used as an open redirect. Mint a nonce with `crypto.randomUUID()`. Put `${nonce}:${returnTo}`
in the state cookie and send ONLY the nonce as the `state` query parameter, so the value an
attacker can see and edit carries nothing the server trusts. Derive the origin from
`x-forwarded-proto` / `x-forwarded-host` exactly as api/checkout.js lines 109-111 do. Return a 302
to `https://accounts.google.com/o/oauth2/v2/auth` with `client_id`,
`redirect_uri=${origin}/api/auth/callback`, `response_type=code`, `scope=openid email profile`,
`state`, `access_type=online`, `prompt=select_account`, and the state Set-Cookie header. The scope
string is exactly those three values — nothing wider.

**api/auth/callback.js** (`export async function GET(request)`) — finish the flow.
Read `code` and `state` from the URL and the nonce/returnTo pair from the state cookie. On any
mismatch, missing value, or missing code, redirect 302 to `/?auth=failed#subscribe` with the state
cookie cleared. Never reveal which check failed and never render a message (D-07).
Exchange the code at `https://oauth2.googleapis.com/token` with a form-encoded POST carrying `code`,
`client_id`, `client_secret`, `redirect_uri` (byte-identical to the one api/auth/google.js sent —
Google compares them) and `grant_type=authorization_code`.
Split the returned `id_token` on `.` and base64url-decode the payload. Validate `aud` equals
`GOOGLE_CLIENT_ID`, `iss` is `accounts.google.com` or `https://accounts.google.com`, `exp` is in the
future, and `email_verified` is exactly `true` — an unverified Google email is not proof of
anything. The signature is deliberately not checked locally; add a comment recording why: the token
came straight back from Google's own token endpoint over TLS in a server-to-server call, the case
Google's documentation explicitly exempts. Any failed check takes the same silent
`/?auth=failed#subscribe` path.
Then `await ensureSchema()`, `await upsertUser({ sub, email, name, picture })`, sign a session over
`{ uid, email, name }`, and 302 to `/#${returnTo}`. Two cookies go out at once (set session, clear
state), so build the response with `new Headers()` and call `headers.append('Set-Cookie', ...)`
twice — the plain-object headers form carries a single Set-Cookie and would silently drop one.
