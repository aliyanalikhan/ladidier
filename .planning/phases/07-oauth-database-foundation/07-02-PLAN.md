<objective>
Make the identity from Plan 01 visible and operable in the UI: one place in `App` that knows who is
signed in, a small sign-in indicator in the main Nav, and a sign-in / sign-out row on the Subscribe
page.

Purpose: Plan 01 proved the round trip with curl and a hand-driven browser redirect. AUTH-01,
AUTH-02 and AUTH-03 are only actually true for a visitor once there is a way in, a way out, and a
visible answer to "am I signed in?" that survives a reload. This plan expands outward from the
proven tracer without adding any new server surface.

Output: an `/api/auth/me` effect and `user` / `authReady` state in `src/app.jsx`, a new `.nav-signin`
element and CSS rule, and the Subscribe page sign-in row.

Locked decisions this plan implements:
- D-04: a sign-in indicator is added to the main Nav in addition to the draft plan's Subscribe-page row — "Sign in" when signed out, the person's Google name or email when signed in, and clicking it routes to the Subscribe page rather than opening a menu.
- D-05: the existing `#account` EN · USD anchor is a dead language/currency stub, not an account link, so a separate new Nav element is added and that stub is left byte-for-byte untouched.
- D-07: no visible error surface is built for a failed sign-in anywhere in the UI — no banner, toast, or inline message; the visitor simply arrives back signed out.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> /api/auth/me | The only channel by which the client learns who it is; the answer is per-visitor and must not be cached or persisted. |
| server identity claims -> DOM | A Google-supplied `name` and `email` are rendered into the page as text. |
| client `user` state -> UI decisions | The browser's copy of the identity is display-only and must never be the thing that authorises anything. |

## STRIDE Threat Register

ASVS level: 1 · Block-on severity: high

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-14 | Elevation of Privilege | client `user` state in `src/app.jsx` | high | mitigate | The `user` object drives display only. Nothing in this plan grants access, unlocks content, or skips a server check based on it. Every authorisation decision stays server-side against the httpOnly cookie (Plan 01's `readSession`, Plan 03's checkout 401). |
| T-07-16 | Information Disclosure | identity in browser storage | medium | mitigate | The identity is never written to `localStorage` or `sessionStorage`; it is re-derived from the httpOnly cookie on every load. Asserted by the unchanged `localStorage.setItem` count gate in Task 1. |
| T-07-17 | Tampering | Google `name` / `email` rendered into the DOM | low | accept | React escapes interpolated text by default and neither value reaches `dangerouslySetInnerHTML`, a URL, or an attribute other than `title`. Accepted rather than sanitised because adding an escaping layer on top of React's own would be redundant. |
| T-07-18 | Information Disclosure | `/api/auth/me` response in a shared cache | medium | mitigate | Already mitigated server-side in Plan 01 by `Cache-Control: private, no-store` on both branches. This plan adds no caching layer, no service worker, and no client-side response store on top of it. |
| T-07-SC | Tampering | package-manager installs | n/a | mitigate | No `npm install` occurs in this plan — it adds no dependency. The phase's single new package was gated by the blocking human legitimacy checkpoint in 07-01-PLAN.md Task 1. |
